# 规格增量：订阅计费分组限定

## Purpose

本能力限定各订阅套餐可以为哪些实际请求分组计费，同时保持 API Key 分组授权、用户所属分组和钱包计费相互独立。

## ADDED Requirements

### Requirement: 管理员配置套餐计费分组
系统 SHALL 允许管理员独立于「升级分组」设置套餐的「计费分组限定」。限定为空时，所有其他条件允许的分组均可使用该订阅计费；现有套餐默认保持这一行为。

#### Scenario: 限定为单个分组
- **WHEN** 管理员将套餐计费分组限定保存为 `default`
- **THEN** 套餐展示该限定，且只有实际使用 `default` 分组的请求能够消耗该订阅

#### Scenario: 不设置分组限定
- **WHEN** 管理员保存未设置计费分组限定的套餐
- **THEN** 其他权限允许的任意分组请求仍可使用该订阅计费

#### Scenario: 拒绝不存在的分组
- **WHEN** 管理员提交不存在的计费分组
- **THEN** 创建或更新套餐失败，且原套餐配置不变

### Requirement: 已售订阅使用套餐当前配置
系统 SHALL 对每次订阅计费请求读取套餐当前的分组限定，MUST NOT 将购买时的限定固化在用户订阅实例中。

#### Scenario: 管理员修改已有套餐
- **WHEN** 用户持有有效订阅期间，管理员修改该套餐的计费分组限定
- **THEN** 此后使用该订阅的请求立即按新的限定判断，已购买的订阅实例无需修改

### Requirement: 只有匹配分组的订阅可以计费
系统 MUST 在消耗订阅前比较请求实际路由到的分组与候选套餐的计费分组限定。服务端 MUST 对已有 API Key 和直接 API 请求同样执行此校验。

#### Scenario: 匹配分组消耗订阅
- **WHEN** 用户持有仅限默认组的日卡，并发送实际路由到 `default` 的请求
- **THEN** 该请求可按照现有订阅额度规则消耗日卡

#### Scenario: 不匹配分组改扣钱包
- **WHEN** 用户仅持有默认组日卡，发送实际路由到 `gpt-stable` 的请求，且钱包额度充足
- **THEN** 请求从钱包扣费，日卡已用额度不变

#### Scenario: 仅订阅偏好下分组不匹配
- **WHEN** 用户选择「仅订阅扣费」，但请求分组不在任何有效订阅的计费范围内，且钱包额度充足
- **THEN** 作为分组不匹配的例外，请求从钱包扣费，不消耗订阅

#### Scenario: 不匹配分组且钱包不足
- **WHEN** 用户仅持有默认组日卡，发送实际路由到 `gpt-stable` 的请求，且钱包额度不足
- **THEN** 请求因钱包额度不足失败，日卡已用额度不变

#### Scenario: 多个有效订阅
- **WHEN** 用户持有多个有效订阅，只有其中一个允许请求实际分组
- **THEN** 只有允许该分组的订阅可以为请求计费

#### Scenario: 自动分组使用实际分组
- **WHEN** 自动分组 API Key 将请求路由到具体分组
- **THEN** 系统按该具体分组判断订阅资格，而不是按 `auto` 选择器判断

### Requirement: 向购买者展示分组限定
系统 SHALL 在套餐管理和购买界面展示套餐的计费分组限定或「不限制」状态，并明确其不是 API Key 分组权限限制。

#### Scenario: 购买者查看受限套餐
- **WHEN** 购买者查看计费分组限定为 `default` 的套餐
- **THEN** 购买前可看到该订阅只能为 `default` 分组请求计费
