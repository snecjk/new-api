# Design

## Context

`model/subscription.go` 已有套餐、用户订阅、余额购买和幂等支付完成逻辑；`middleware/model-rate-limit.go` 目前仅按用户/分组限流。订阅在预扣费时才选定，不能在更早的限流中间件中猜测目标订阅。

## Goals / Non-Goals

**Goals:** 复用现有订阅和支付链路，令配置、订单、权益与限流一致。

**Non-Goals:** 引入新支付服务、改变订阅额度结算规则、提供独立有效期或自动续购。

## Decisions

1. **权益按订阅保存。** 套餐增加基础 RPM，购买时快照到订阅；独立加购档位关联套餐，包含 RPM 增量、金额、启用状态及现有支付渠道需要的商品标识。相比直接改用户分组，可避免影响其他订阅及钱包请求。
2. **复用支付，区分订单用途。** 订阅订单增加用途、目标订阅及档位价格/增量快照；余额扣款与权益更新同事务，外部支付沿用签名、金额、币种和渠道校验。完成回调按用途分派，禁止将加购误处理为新订阅。相比另建支付体系，保留现有渠道配置和账务入口。
3. **发放严格一次。** 锁定订单与订阅后校验归属、状态及到期时间，成功订单不可重复发放；付款时原订阅已失效则记录待退款状态，不给失效订阅发权益。档位改价不影响已有订单。
4. **对已选订阅限流。** 在计费确定订阅、调用上游之前执行专用检查；使用订阅 ID 作为跨令牌计数键，采用原子滚动窗口计数，Redis 支持多实例，无 Redis 时使用加锁内存实现。超限走现有撤销预扣路径，不能回退钱包或其他订阅。保留原全局/分组限流，不直接覆盖其配置。
5. **界面仅暴露业务配置。** 套餐表增加 RPM 列，编辑抽屉增加基础 RPM 与加购档位；钱包已购订阅卡增加 RPM 明细、档位选择和购买确认。服务端计算价格，支付发放后刷新权益并失效相关缓存。
6. **输入与金额有界。** 基础/增量 RPM 上限统一为 1000000，叠加结果不得超过此值；价格沿用套餐的正金额范围（不超过 9999）及精度规则。非法、非有限数值拒绝；余额金额转换沿用安全配额转换，不使用裸整型转换。

## Risks / Trade-offs

- 多实例计数或缓存陈旧导致超发 → Redis 原子检查并记录，权益更新后使缓存失效；内存模式仅承诺单实例。
- 余额与异步回调并发导致重复权益 → 唯一订单、事务锁、订单终态校验与回归测试。
- 接入限流后已预扣额度未退还 → 通过计费会话统一撤销预扣，验证 429 不产生消费。

## Migration Plan

采用兼容 SQLite/MySQL/PostgreSQL 的新增表和列。本提案建议已有套餐和订阅补齐 5 基础 RPM、0 加购 RPM，新订阅快照套餐配置；上线说明需提示现有订阅限流变化。先部署后端与迁移，再部署前端；回滚时关闭新入口及专用限流、保留订单与权益数据，已付款订单继续对账。
